# Завершене встановлення Detent: скіли, постійний CLI та дозволи агентів

Дата: 2026-11-09
Статус: чекає на затвердження — перевірку сумісності з Claude власник провів, запуск розділено за хостами; потрібен повторний cross-review; реалізацію не дозволено
Spec-review: claude/default @ f36e370 (author: codex) — 10 findings: 9 fixed, 1 rejected

## Для власника

### Мета

Покращити сумісність із Codex, не порушивши сумісності з Claude. Після завершення
встановлення всі чотири скіли доступні в обраних агентах. У Codex їхні команди
використовують уже встановлену версію Detent; Claude Code та Antigravity зберігають
чинний запуск через `npx`. Відомі потреби в дозволах показуються й узгоджуються під час
встановлення, до першого робочого cross-review.

### Що зміниться для тебе

Рекомендований спосіб встановлення — одна явна команда `detent install` із конкретного
релізу. Для набору `.agents` вона залишає постійний CLI навіть у проєкті без `package.json`,
встановлює скіли та проводить налаштування доступу Codex. Завантаження через npm можливе
на цьому кроці; подальші виклики скілів у Codex до npm не звертаються. Саме додавання
npm-залежності ще не означає завершення цього процесу — це окреме рішення для твого
підтвердження нижче.

Для Claude нічого не змінюється: плагін і `.claude/skills` запускають ту саму команду
`npx -y @ysilvestrov/detent cross-review`, що й зараз, байт у байт; наявні allow-правила
користувачів продовжують спрацьовувати. Antigravity теж лишається на `npx`: він і так
вимагає ручного кроку — додати команду в дозволи в налаштуваннях проєкту; інсталятор
показує цю точну команду.

Користувач бачить, які дії дозволяє, для якого проєкту, версії й агента. Якщо середовище
не дозволяє зберегти дозвіл або потребує нового сеансу, інсталятор це повідомляє до завершення.
Гарантії «ніколи більше не запитає» немає: організаційна політика й нові дії мають пріоритет.
Встановлення лише `--claude` зберігає чинні exit-коди. Коли встановлюється `.agents`,
для неінтерактивного повного setup потрібен явний вибір хостів `--hosts`; старі scripts,
які вважали exit 0 лише успіхом копіювання, потребують міграції: неповний setup повертає 6.

### На чому стоїть рішення

- Усі скіли мають бути доступні після встановлення, необхідні дозволи запитуються тоді ж.
  `[вимога власника]`
- До реалізації власник перевіряє специфікацію з іншими агентами. `[вимога власника]`
- Задача — покращити сумісність із Codex, не порушуючи сумісності з Claude; часткове
  дублювання прийнятне. Antigravity лишається на `npx`, бо дозвіл у ньому однаково
  додається вручну в налаштуваннях проєкту. `[вимога власника]`
- Єдиний проєктний launcher для всіх хостів ламає Claude: кожна десктопна сесія Claude Code
  працює в новому worktree без ігнорованого runtime; плагін читає той самий `skills/`, тож
  користувачі лише плагіна втратили б робочий cross-review; постійний allow на змінюваний
  проєктний JS заборонено цим же дизайном. `[перевірка власника]`; `[проба]` П-6.
- Чинний пакет доставляє чотири скіли, але `npm install` не виконує їх встановлення;
  `install` не налаштовує дозволи. `[проба]` П-1, П-2.
- Робота без `package.json` — чинна вимога попередньої затвердженої специфікації;
  її збереження тут є рішенням автора. `[проба]` П-4; `[виведення]` щодо нового рішення.
- Механізм збереження доступу залежить від агента та його версії; універсальної доведеної
  інтеграції наразі немає. `[проба]` П-5; `[виведення]` для неперевірених агентів.
- Припущення, що кожен обов'язковий хост має read-only спосіб довести застосування правил,
  **не перевірено**. `codex execpolicy check` над файлом не доводить, що desktop завантажив
  його. За відсутності іншого доказу повний setup не може отримати exit 0; критерій треба
  переглянути з власником до реалізації. `[виведення]`

### Ключові рішення

1. **Явний єдиний `install`, без обов'язкового `postinstall`.** Альтернатива — змінювати
   проєкт у npm lifecycle hook; відкинуто як основний шлях через вимкнені scripts,
   неінтерактивне CI й ненадійний канал для згоди. Потрібне підтвердження власника, чи це
   відповідає його розумінню «після встановлення пакету».
2. **Запуск окремий для кожного хоста.** Команда запуску в скілах, конституції та форматі
   спеки стоїть у блоці `detent:run`, який інсталятор переписує за target, як уже
   переписує блок `detent:author`. Claude (плагін, `.claude/skills`, `CLAUDE.md`) отримує
   чинний `npx` без змін; спільна копія `.agents` — умовний рядок: launcher у Codex, `npx`
   в Antigravity. Альтернатива — один launcher для всіх хостів; відкинуто, бо він ламає
   Claude (worktree, плагін, постійний дозвіл, блокування версії при оновленні плагіна).
   Ціна — дві команди запуску в текстах і перевірка їхньої узгодженості під час випуску.
3. **Самодостатній runtime у проєкті для Codex, однаковий з версією скілів.** Альтернатива —
   лише `node_modules` або глобальний CLI; відкинуто як єдине джерело, бо вони не покривають
   одноразову інсталяцію без npm-проєкту та переносимість. Мовчазного fallback до `npx` у
   Codex-гілці немає; `npx` у Claude та Antigravity — їхній власний шлях, а не fallback.
4. **Дозволи через перевірений механізм кожного агента, з окремою згодою на їх збереження.**
   Альтернатива — загальне «довіряти Detent назавжди» в інструкціях; воно не є доказом
   конфігурації хоста. Автоматичне послаблення глобальної або керованої політики відкинуто.
   Постійний дозвіл запускати змінюваний проєктний JS поза sandbox заборонено: digest,
   який перевіряє сам цей JS, не захищає від підміни. Якщо хост підтримує лише такий
   дозвіл, setup лишається неповним; довірений runtime поза доступом агентних записів
   потребуватиме окремо затвердженої зміни архітектури. Адаптери дозволів пишуться лише
   для Codex CLI та Codex desktop. Antigravity — ручний хост: інсталятор показує точну
   команду для дозволів проєкту і нічого не записує. Claude не є хостом налаштування
   доступу в цій зміні: його шлях запуску не змінюється.
5. **Точний звіт про незавершені кроки.** Встановлені файли, виявлена конфігурація й
   перевірений запуск — різні факти. Альтернатива — загальний зелений статус після копіювання.
6. **Перевірка сумісності блокує реалізацію адаптерів.** Точні поля налаштувань Codex тут
   не вигадуються. Обов'язкові чотири поверхні: Codex CLI, Codex desktop, Claude Code та
   Antigravity. Для Codex перевіряються скіли, launcher і дозволи; для Claude Code та
   Antigravity — що нова сесія бачить скіли й виконує `npx`, як до зміни. Сумісність усіх
   трьох агентів — критерій приймання, а не припущення з присутності їхніх executable.

Розглянуто стандартне: нативні плагіни — залишаються додатковим каналом скілів; вони не є
єдиним шляхом, бо чинний Claude-плагін не встановлює конституцію та не покриває інших агентів.

Розглянуто стандартне: `npm install --prefix <runtime> --ignore-scripts` — відкинуто для
основного bootstrap цього дизайну. Воно працює без кореневого `package.json` і дає registry
integrity, але повторно резолвить/отримує пакет після вже дозволеного bootstrap та лишає
залежність від npm-кешу на цьому кроці. Копіюємо вже отриманий самодостатній реліз; його
хеші доводять лише цілісність копії. Якщо з'являться runtime-залежності, вибір переглядається.

Правила доступу тут лише локальні для користувача й конкретного проєкту, не комітяться.
Немає автоматичного редагування глобальної чи керованої політики; якщо хост не підтримує
такий scope, потрібне нове рішення власника. Точна версія runtime вимагається лише
Codex-гілкою; plugin-скіли Claude runtime не потребують. Пошкоджена копія відновлюється
новою генерацією без видалення старої.

### Що стане гірше

Локальна копія runtime займає додаткове місце, зокрема в проєкті лише з Antigravity:
інсталятор не відрізняє його від проєкту з Codex. Оновлення Codex-гілки потребує явного
повторного встановлення; Codex у проєкті без залежності більше не підхоплює новий CLI через
`npx` автоматично. Клон потребує відновлення ігнорованого runtime. У текстах скілів дві
команди запуску (`npx` для Claude й Antigravity, launcher для Codex), їхню узгодженість
перевіряє випуск. З'являється підтримка матриці версій агентів; для непідтримуваного
хоста встановлення може завершитися частково. Зміна install exit-кодів для набору `.agents`
несумісна зі старими scripts; `--permissions skip` повертає 6 з явним `filesInstalled=true`.
Успішний `--dry-run` зберігає exit 0 як виняток для плану. Для Claude нічого з цього не
змінюється.

### Оцінка

Власник: **L**. Автор: **L**. Орієнтовна розбивка обсягу: runtime і транзакція встановлення
35%, скіли та міграція 15%, адаптери доступу 25%, міжагентні перевірки та документація 25%.
Розмір зумовлений також перевіркою в зовнішніх агентних середовищах. Це оцінка майбутньої
реалізації, а не розміру цього документа; план і кількість PR ще не затверджено.

Дешевший варіант: лише локальний CLI та правка текстів. Він прибирає runtime-завантаження,
але не виконує вимогу про дозволи під час встановлення та перевірену готовність агентів.

### Питання до власника

1. Чи прийнятно вважати встановленням одну явну команду `detent install`, а звичайний
   `npm install` — лише доставкою пакета? Якщо ні, потрібне рішення про lifecycle hook.
2. Підтвердити матрицю клієнтів і механізми постійних дозволів Codex у розділі
   «Сумісність»; непідтверджена клітинка не дає права заявити повну сумісність або
   реалізувати адаптер.

Вирішено власником 2026-11-09: запуск розділено за хостами; Claude і Antigravity лишаються
на чинному `npx`; Antigravity — ручний хост, що не блокує exit 0; встановлення лише
`--claude` зберігає чинні exit-коди; без TTY і без `--hosts` при наборі `.agents` — exit 6
з `filesInstalled=true`.

## Контекст і межі

Вхідний бріф описує одну відмову автоматичного review до виконання
`npx -y @ysilvestrov/detent cross-review --help`. Після згоди власника запуск у тій сесії
став можливим. Повний журнал тут відсутній: завантаження пакета і збереження дозволу
між сесіями не доведені. Це свідчення власника, не локальне відтворення.

Окремий npm `ENOENT` відстежується в [issue #29](https://github.com/ysilvestrov/detent/issues/29).
Його відтворення, лікування кешу й автоматичні повтори не входять у цю зміну.

Інші виключення: встановлення чи логін reviewer CLI, публікація npm-релізу агентом,
зміна сімейств/моделей рев'юерів, перепроєктування PR-review, автоматична публікація PR,
новий MCP-сервер або обхід відмови політики. Права reviewer-процесу залишаються обмеженими
чинними адаптерами; згода на Detent не означає необмежений доступ його дочірнім агентам.

### П-5. Дозволи: джерела й межі перевірки

Офіційні [правила Codex](https://learn.chatgpt.com/docs/agent-configuration/rules)
описують `.rules`, довіру до проєктного конфігураційного шару та перевірку правила через
`codex execpolicy check`. [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)
окремо описує review запитів і доповнення політики `extra_policy`. Це документація,
не доказ застосування правил у поточному desktop-хості.

[npm lifecycle scripts](https://docs.npmjs.com/cli/v11/using-npm/scripts/)
не є універсальним інтерактивним механізмом згоди агента; scripts можуть бути вимкнені.

`Get-Command claude,codex,agy` знаходить три executable на цій машині. Проба не доводить
авторизацію, доступність моделі, підтримку налаштувань або pickup скілів. Нових сесій
Claude Code, Codex і Antigravity для цієї специфікації ще не запускали.

### П-6. Claude: плагін, worktree і переписування блоків

База: checkout `6e907c3`, Windows, 2026-11-09. `.claude-plugin/marketplace.json` має
`source: "./"`, а `src/plugin.test.ts` вимагає, щоб плагін не мав власного шляху скілів:
плагін і інсталятор читають той самий `skills/`. У цьому репозиторії `.claude/settings.local.json`

команди запуску за target має готовий механізм.

## Запропонований контракт встановлення

### Вхід і доставка runtime

Зберегти `install`, `--claude`, `--agents`, `--superpowers yes|no`, `--dry-run`.
Без target-прапорів встановлюються обидва чинні набори; `.agents/skills` спільний для
Codex і Antigravity, тому для них не створюються дублікати скілів.

Каталоги скілів та хости для налаштування доступу — окремі множини. Додати
`--hosts <comma-separated ids>` з ідентифікаторами `codex-cli`, `codex-desktop`, `agy`.
Прапор не змінює набір скілів. Сам факт присутності executable не вибирає хост.
`codex-cli` і `codex-desktop` мають адаптери дозволів. `agy` — ручний хост: інсталятор
друкує точну команду `npx -y @ysilvestrov/detent cross-review`, яку користувач додає в
дозволи Antigravity в налаштуваннях проєкту; статус «ручний крок показано» не блокує
exit 0. `claude` не є id цього прапора: шлях запуску Claude не змінюється, тож налаштування
доступу для нього немає; `--hosts claude` — usage exit 2 з поясненням.

Крок доступу існує лише тоді, коли встановлюється набір `.agents`. Встановлення лише
`--claude` не питає хостів, не створює runtime і повертає чинні exit-коди. Для `.agents`
без `--hosts` інтерактивний setup просить вибрати хости; без TTY повертає exit 6 з
`filesInstalled=true` та інструкцією повторити з явним вибором. Хост, якого користувач не
обрав, не є відсутньою залежністю; у звіті він «не обрано». Порожній або невідомий id —
usage exit 2.

Приклад bootstrap з явною версією релізу:

```text
npx -y @ysilvestrov/detent@<version> install
```

Він дозволений лише як документований крок встановлення/оновлення. Якщо пакет уже є
локально, підтримується `node ./node_modules/@ysilvestrov/detent/dist/cli.js install`.
Bare `npx detent` не використовується. Глобальний пакет може бути джерелом явного install,
але не стає прихованим runtime для скілів.

Коли встановлюється набір `.agents`, `install` копіює самодостатні файли свого релізу в нову генерацію
`.detent/runtime/<version>/<digest>/<generation>/`:
`package.json`, `dist/`, `prompts/`, `skills/`, `constitution/`. Жодної повторної npm-інсталяції
всередині цієї операції немає. Поточний пакет не має runtime-залежностей; поява таких
залежностей потребує зміни цього контракту, а не неповного копіювання.

У проєкті створюється переносимий launcher `.detent/run.mjs`:

```text
node .detent/run.mjs cross-review --author <id>
node .detent/run.mjs doctor
```

Launcher прив'язаний до конкретної версії та digest встановленого набору; визначає файли
від власного URL, а проєкт — від свого розташування. Запуск з підкаталогу в інструкціях
завжди посилається на launcher від кореня проєкту; абсолютні машинні шляхи не комітяться.
Не можна дозволяти довільний зовнішній шлях до runtime через state/config.
Відносна активна generation лежить у машинному `.detent/local/runtime.json`; launcher
приймає лише шлях усередині зазначеного version/digest, без symlink-escape. Цей pointer
не є доказом довіри чи дозволу на виконання поза sandbox.

Linked worktree (зокрема worktree десктопної сесії Codex) не має власного runtime і pointer.
Якщо їх немає поруч із launcher, launcher визначає головний checkout через
`git rev-parse --git-common-dir` і шукає runtime лише за точним шляхом
`.detent/runtime/<version>/<digest>/` того checkout'а, з тим самим pointer, перевіркою
інвентарю/хешів і забороною symlink-escape. Шлях визначає Git, а не state/config, тому це
не довільний зовнішній шлях. Без runtime в головному checkout — та сама відмова з
інструкцією встановити потрібну версію.

Команда запуску в активних скілах, конституції, форматі спеки й прикладах стоїть у блоці
`<!-- detent:run begin -->` … `<!-- detent:run end -->`, який інсталятор переписує за
target так само, як блок `detent:author`:

- джерело `skills/`, Claude-плагін, копії `.claude/skills` і блок конституції в `CLAUDE.md`
  містять чинний рядок `npx -y @ysilvestrov/detent cross-review …` без змін;
- копії `.agents/skills` і блок у `AGENTS.md` містять умовний рядок: у Codex —
  `node .detent/run.mjs --expect-version <version> cross-review …`, в Antigravity —
  чинний `npx -y @ysilvestrov/detent cross-review …`.

Маркери стоять окремими рядками поза code fence і охоплюють цілий фрагмент — абзац або
блок коду; речення, де команда зараз вбудована в текст (конституція, `design-spec`), для
цього виносять команду в окремий фрагмент. Поле `description` у frontmatter скілу не
містить команди («запускає Detent cross-review»), щоб frontmatter не потребував маркерів.
Отже, для Claude змінюються лише маркерні рядки, межі фрагментів і `description`; сам
рядок запуску лишається байт у байт. Історичні спеки та результати минулих рев'ю не
переписуються.

Codex-рядок несе точну required-version релізу; узгодженість цього маркера з package
version перевіряється під час випуску разом зі збігом двох команд за підкомандами й
прапорами. Launcher отримує `--expect-version <version>` перед підкомандою, відмовляє до
запуску runtime за розбіжності й пропонує явно оновити setup. Claude-плагін і Antigravity
runtime не використовують, тож оновлення плагіна не впливає на runtime проєкту. Якщо
plugin та копії скілів у `.claude/skills` дублюються, зберігається попередження; їх не
видаляють автоматично.

### Стан на диску та повторюваність

- Launcher і потрібна версія/хеші входять до контрольованого installer manifest разом зі
  скілами. Схема нового manifest має явну версію; читання старого формату підтримується.
- `.detent/runtime/` та машинний стан `.detent/local/` додаються в `.gitignore`;
  launcher і manifest придатні для Git. У manifest немає секретів, машинних абсолютних
  шляхів, згоди людини або заяви про перевірений доступ іншої машини.
- Перед записами будується повний план і перевіряються конфлікти. Редаговані файли,
  alias, symlink/junction за межі дозволених каталогів та невідповідний runtime при запуску — відмова,
  а не привід перезаписати чи завантажити щось мовчки. Файли runtime перевіряються за
  інвентарем/хешами; це контроль цілісності, не підпис автора пакета.
- Паралельні `install` серіалізуються lock-файлом; при зайнятому lock другий запуск
  завершується з поясненням. Після аварії lock не знімають лише на підставі віку: показують
  його власника, безпечне ручне відновлення не видаляє runtime чи скіли.
- Runtime готується до переключення launcher; активна версія змінюється лише після
  успішної перевірки набору. При I/O-збої можливі неактивні залишки, але старий launcher
  не повинен вказувати на неповну нову версію. Manifest записується останнім; `doctor`
  виявляє перерване оновлення й не називає його успішним.
- Пошкоджена generation ніколи не перезаписується і не видаляється. Повторний явний
  `install` із чистого джерела тієї самої версії готує нову generation, перевіряє її та
  перемикає локальний pointer. При зміні source digest без зміни version потрібна
  явна згода на показаний diff нового набору (локальна збірка теж не виняток).
  `doctor` показує точну команду такого repair і залишені неактивні каталоги.
- Повтор тієї ж версії ідемпотентний. Старі runtime-каталоги не видаляються автоматично.
  `--dry-run` не пише файли, не бере lock і не запускає prompts, рев'юерів чи модель.
- Клон з відсутнім runtime отримує явну інструкцію встановити потрібну версію; linked
  worktree використовує runtime головного checkout'а за правилом вище. Runtime-виклик не
  ремонтує середовище через мережу.

Точний формат manifest, lock і алгоритм відновлення після збоїв — рішення реалізатора
в межах наведених інваріантів; переривання між записами має окремі acceptance-сценарії.

## Дозволи під час встановлення

### Обсяг згоди

До застосування змін користувач бачить план файлів та окремо пропозицію доступу:
ідентичність пакета, версію, корінь проєкту, спосіб запуску, тимчасові файли й worktree,
reviewer CLI з конфігурації та можливе використання їхніх сервісів/лімітів.
Згода на інсталяцію не включає публікацію PR, читання сторонніх credential-файлів,
довільні команди `node`/`npx` або всі майбутні версії Detent.

Новий параметр `--permissions ask|apply|skip`, типово `ask`. Він діє лише на хости з
адаптерами (`codex-cli`, `codex-desktop`); для `agy` будь-який режим лише показує ручну
інструкцію, нічого не записуючи. При встановленні лише `--claude` параметр не має кроку,
до якого застосовуватись, і не змінює exit-коду.

- `ask`: запропонувати вузькі правила для доступних підтримуваних хостів. Запис
  конфігурації дозволів потребує явного підтвердження її точного diff та scope.
- `skip`: встановити файли без зміни дозволів, у звіті показати пропущений крок;
  він не означає готовність до unattended cross-review.
- Без TTY `ask` не висить і не приймає згоду автоматично. CLI формує пропозицію;
  якщо запуск ініціював агент, той передає її у свій нативний механізм підтвердження.
  Якщо доступного каналу немає — результат «потрібна дія користувача».
- `apply --proposal <path> --expect-hash <sha256>`: застосувати раніше показаний локальний
  план через той самий адаптер. `ask` у неінтерактивному режимі готує proposal у
  `.detent/local/` і друкує точну apply-команду. Після явної згоди користувача агент
  виконує її через нативний approval-механізм хоста; без такого механізму користувач
  запускає команду сам. Proposal містить version/digest runtime, корінь, host ids,
  точний diff, дозволені локальні шляхи й хеші попереднього вмісту. Перед записом adapter
  повторно перевіряє всі ці дані; будь-яка зміна робить план застарілим, без записів.
  Параметр `apply` і proposal самі не є дозволом хоста; його політика може відхилити
  команду. Інтерактивний `ask` після згоди користується тією ж процедурою apply.

Просте підтвердження в CLI фіксує згоду на зміну конфігурації, але не підміняє запит
хоста й не доводить, що він завантажив конфігурацію. Інсталятор не може видати сам собі
дозвіл, змінити керовані обмеження або обіцяти, що всі можливі наступні дії вже дозволені.
Правила пишуться лише в документоване user-local/project-scoped місце, яке не потрапляє
в Git. Точний підтриманий шлях є частиною compatibility gate кожного адаптера; перелік
дозволених шляхів закритий, з proposal не приймаються довільні абсолютні targets.
Налаштування Claude Code (`.claude/settings.json`, `.claude/settings.local.json`) і
Antigravity інсталятор не редагує взагалі; спільна `.codex`-конфігурація, глобальні правила
й повна політика Auto-review не редагуються. Для хоста без відповідного scope setup лишається
неповним до нового рішення власника. Ручне адміністрування глобальної політики поза
цим дизайном не видається за дію інсталятора.

Згода та локальна діагностика не комітяться. При зміні версії, launcher/runtime digest,
проєкту, обсягу дій або активної політики попереднє підтвердження не є доказом для нового
контексту. Інсталятор показує, що потребує повторної перевірки. Скіли не трактують
збережений локальний receipt як дозвіл на дії, відхилені хостом.

### Коли налаштування доступу завершене

Для кожного явно обраного хоста з адаптером (`codex-cli`, `codex-desktop`) адаптер має заново отримати його нативну read-only
діагностику активних правил: версію/ідентичність хоста, корінь, scope та рішення щодо
конкретної команди launcher. Діагностика має підтверджувати, що конфігурація застосована
і додаткове погодження для цієї команди не потрібне. Лише запис файла або згода в CLI
цього стану не встановлюють. Якщо нативна діагностика не існує чи потребує перезапуску,
стан лишається «потрібна дія»; адаптер не імітує її результатом іншого CLI.

Для обраного `agy` крок завершений, коли інсталятор показав точну команду й місце в
налаштуваннях проєкту Antigravity; статус «ручний крок показано» означає саме це, а не
перевірене застосування правила. Він не блокує exit 0 — так само, як чинний ручний крок.

`permissionSetupComplete` означає лише проходження цього setup-контракту для обраних
хостів у поточному контексті. Воно не обіцяє відсутність відмов під час фактичного рев'ю.
Результат live cross-review записується окремо і не є зворотним каналом видачі дозволу.
Після перезапуску користувач повторює той самий `install --hosts ...`; ідемпотентна
файлова частина не змінюється, а нативна діагностика виконується заново. Імпортувати
довільний файл «згода отримана» або довіряти старому receipt заборонено.

На перевірці сумісності треба довести саме цей read-only зворотний канал. Якщо хост
його не має, до затвердження змінюється критерій повного setup для цього хоста або
явно приймається обмеження exit 6. Цю продуктову поступку не залишають реалізатору.

### Сумісність: предмет перевірки до реалізації

| Агент/поверхня | Доставка скілів | Запуск | Механізм доступу | Що треба підтвердити |
|---|---|---|---|---|
| Codex CLI | `.agents/skills` | launcher | адаптер: нативна діагностика rules; збереження доступу лише без виходу змінюваного JS за sandbox | версія CLI, project scope, форма argv, фактичне застосування, незалежна межа довіри, linked worktree, нова сесія |
| Codex desktop | `.agents/skills` | launcher | адаптер: механізми активного хоста; не припускати тотожність CLI | підтримка локальних rules/policy, managed-обмеження, UI підтвердження, worktree сесії |
| Claude Code | `.claude/skills` або чинний plugin | `npx`, без змін | без змін; інсталятор нічого не пише | нова сесія (зокрема в worktree десктопа) бачить скіли й виконує ту саму команду `npx`, що до зміни; наявні allow-правила спрацьовують |
| Antigravity | `.agents/skills` | `npx`, без змін | ручний: інсталятор показує команду для дозволів проєкту | нова сесія обирає Antigravity-рядок блоку `detent:run` і виконує `npx` після ручного дозволу |

Author-хост та reviewer-процес — різні ролі: чинна deny rule reviewer `agy` не є
підтвердженням дозволу author-хосту запускати Detent. Вибір `--author` і правило іншого
модельного сімейства не змінюються.

У кожному адаптері Codex треба фіксувати підтримувані перевірені версії, джерело документації,
scope правил, приклади дозволених/недозволених команд і спосіб скасування власних змін.
Невідомий клієнт/версія → «не перевірено» та інструкція; файли скілів доступні, але
сумісність дозволів не заявляється. Відсутність механізму хоча б в одному обов'язковому
хості повертає до власника обмеження цілі — не дозволяє мовчки прибрати хост із матриці.

Для Codex не встановлювати широкий prefix `node`/`npx`, не замінювати повну політику
Auto-review і не змінювати глобальні налаштування. **Не створювати persistent allow поза
sandbox для проєктного launcher або runtime:** агент чи checkout іншої гілки може змінити
їх, а самоперевірка mutable JS не встановлює межу довіри. Claude та Antigravity цієї
заборони не торкаються: вони запускають пакет із реєстру, який агент змінити не може,
а не проєктний JS. Допустимий persistent механізм має зберігати поточні filesystem
і network межі або доводити незмінність коду через незалежний від проєктного JS механізм
хоста. У поточному дизайні такого механізму не доведено; це blocking compatibility gate.
Потреба виходу cross-review за sandbox (зокрема запис до git metadata) не обходиться:
без підтриманого вузького механізму хост лишається «потрібна дія», а повторні запити
доступу є явно незакритою вимогою. Trusted runtime поза writable scope агента — можлива
наступна архітектура, не прихована частина цього install.

## `doctor`, довідка та результати

Додати коректний `--help` для верхнього CLI та кожної підкоманди: exit 0, без git,
конфігурації проєкту, файлових записів, мережі, prompts і запуску рев'юера. Це перевірка
працездатності CLI, не доказ дозволу на повне рев'ю.

`doctor` виконує лише read-only перевірки. Людинозрозумілий вивід та `--json` з версією
схеми показують незалежні поля:

Обов'язкові машинні підсумки: `filesInstalled`, `runtimeVerified`,
`permissionSetupComplete`, `selectedHosts`, `liveReviewVerified`. Останнє — лише
контекстне спостереження; воно не потрібне для exit 0 setup. `doctor` приймає той самий
`--hosts`, а без нього використовує локальний останній явний вибір як налаштування scope;
відсутність вибору означає незавершений setup. Перевірка permissions завжди нативна й
нова, не відтворена з попереднього JSON.
Цей вибір є локальною конфігурацією користувача, не доказом дозволів; вивід завжди називає
джерело scope (`argument` або `local-selection`) і точні hosts. Некоректна локальна
конфігурація — exit 2; новий явний `--hosts` має пріоритет. Зміна цього вибору не дозволяє
заявляти сумісність решти обов'язкової release-матриці.

- runtime: версія, відповідність manifest та інвентарю; для встановлення лише `--claude` —
  «не потрібен» (runtime не створюється, `runtimeVerified` не вимагається);
- skills: очікувані файли/хеші та дублікати; pickup агентом — «не перевірено», поки
  від самого хоста немає доказу;
- reviewers: executable знайдено/не знайдено; логін, модель і сервіс — «не перевірено»
  без окремого звернення до них;
- permissions: для кожного хоста Codex «пропозиція», «конфігурацію записано», «потрібна дія»,
  «відхилено політикою», «не підтримано»; для `agy` — «ручний крок показано»; Claude у
  цьому полі не з'являється; фактичний запуск в окремому полі з контекстом
  і часом перевірки. Це спостереження, а не токен авторизації майбутніх дій.

Зберегти чинні install exit 0/2/4 для завершення, помилки вводу/читання та конфлікту.
Встановлення лише `--claude` повертає тільки їх, з тими самими умовами, що й зараз.
Коли встановлюється набір `.agents`, додається exit 6 «файли встановлено, налаштування
доступу потребує дії»; це стосується й типового запуску без target-прапорів, без TTY і без
`--hosts`. `skip` теж повертає
6, якщо доступ не підтверджено хостом; свідомий пропуск не маскується як повна готовність.
Для автоматизації успішне копіювання видно через `filesInstalled=true` навіть при exit 6.
`--dry-run` повертає 0 за валідного безконфліктного плану й явно називає це планом.
Сухий запуск має пріоритет над усіма setup-передумовами: без TTY і без `--hosts` він
не просить вибір і повертає 0, якщо файловий план валідний; access-план показує
«хости не обрано». Явно помилкові аргументи та файлові конфлікти залишають exit 2/4.
`doctor`: 0 — локальні перевірки пройшли, 2 — пошкоджені дані/usage, 6 — бракує компонентів
чи потрібна дія. За винятком `install --dry-run` і встановлення лише `--claude`, для
install і doctor exit 0 вимагає `filesInstalled=true`, `runtimeVerified=true`,
`permissionSetupComplete=true` для всіх обраних хостів (для `agy` достатньо показаного
ручного кроку); `skip` не встановлює останнє поле. Навіть exit 0 `doctor` не означає доведену
авторизацію повного cross-review.
Цю зміну значення install exit-кодів документувати як міграційну несумісність для scripts.

Реальне рев'ю є окремим явним acceptance-запуском після встановлення: воно може
використати платний сервіс. `install` та `doctor` ніколи не запускають модель непомітно.

## Міграція та межі зворотної сумісності

Нова версія `install` читає старий manifest, планує runtime й launcher та оновлює лише
незмінені керовані тексти. Редаговані скіли/блоки залишаються конфліктом exit 4 без записів.
Перехід із npm-залежності не змінює `package.json`/lock проєкту; оновлення залежності
саме по собі не переключає runtime, доки не виконано `install`.

Статичні скіли Claude-плагіна не переписуються з інсталятора: оновлюється сам plugin-реліз.
Плагін читає джерело `skills/`, де блок `detent:run` містить чинний Claude-рядок `npx`, тож
користувач лише плагіна не потребує bootstrap і нічого не втрачає. Тест плагіна про єдине
джерело `skills/` лишається чинним.
У самому репозиторії Detent bootstrap/рев'ю дозволено робити через `node dist/cli.js` після
збірки, як зараз; Claude-скіли тут працюють через плагін і `npx`, як зараз. Для Codex цей
виняток має бути записаний в інструкціях репозиторію, які Codex читає; опубліковані скіли
не отримують через нього fallback до `npx`.

Нова інструкція не вимагає глобального встановлення або додавання user PATH.
Windows і POSIX запускають той самий `.mjs` через Node; окремі `.cmd` шими не потрібні.
Перевірка перенесення каталогу охоплює пробіли та не-ASCII у шляху.

## Критерії приймання

1. Із релізного tarball одна явна інсталяція працює в Git-проєкті з npm-залежністю
   та без `package.json`; всі чотири скіли й відповідні допоміжні файли доставлено.
2. Після bootstrap, при недоступному npm registry й видаленому тестовому npx-кеші,
   launcher виконує `--version`/`--help`; subprocess trace не містить npm/npx.
   Мережа reviewer-сервісу перевіряється окремо від мережі npm.
3. Матриця Windows + POSIX: повтор install, запуск із підкаталогу, перенесення проєкту,
   пробіли/не-ASCII, клон без runtime, linked worktree з runtime лише в головному checkout,
   відсутній/пошкоджений runtime, відредагований skill/block, старий manifest, паралельні
   install та перерване оновлення.
4. Claude не змінився: у `skills/`, Claude-плагіні, копіях `.claude/skills` і блоці
   `CLAUDE.md` рядки запуску збігаються байт у байт із релізом до зміни (тест на текст;
   інші відмінності — лише маркери, межі фрагментів і `description`);
   встановлення лише `--claude` повертає ті самі exit-коди й не створює `.detent/runtime/`;
   інсталятор не пише в налаштування Claude Code. Копії `.agents` містять обидва рядки
   блоку `detent:run`, і їхні підкоманди та прапори збігаються.
5. Усі `--help` працюють поза Git без записів чи запуску процесів рев'юера, exit 0.
6. `--dry-run`, відмова в згоді, skip, немає TTY, невідомий клієнт, managed deny:
   точний результат; немає прихованого дозволу, глобальної зміни чи заяви «готово».
7. Для кожного обов'язкового хоста зафіксовані версія, ОС, active policy і transcript.
   Codex CLI й Codex desktop: нова сесія (зокрема в worktree) бачить чотири скіли та
   запускає встановлений CLI без звернення до npm; якщо потрібен дозвіл — його запитано
   під час setup; перевірено, що саме збережено й чи зберігається воно після перезапуску.
   Для непостійного дозволу це обмеження видно вже в setup і воно потребує рішення
   власника до реалізації адаптера. Claude Code (CLI і десктоп у worktree) та Antigravity:
   нова сесія бачить чотири скіли й виконує ту саму команду `npx`, що до зміни;
   для Antigravity — після показаного інсталятором ручного дозволу.
8. Явно дозволений контрольний cross-review для кожного підтвердженого хоста завершується
   валідним marker/report; поява worktree й файлів відповідає погодженому scope.
   Auth/ліміт/помилка рев'юера не переписується на помилку дозволів чи успішне рев'ю.
9. Оновлення runtime та підміна launcher в тесті скидають попередню локальну перевірку;
   broad allow для `node`/`npx` не з'являється. Перевірено й негативні приклади команд.
10. `npm run gate` та smoke релізного пакета проходять із новим контрактом.
   CI перевіряє механіку без provider-викликів; live-матриця має окремі докази.

## Заявка → доказ

| Заявка | Де фіксується | Що доводить | Сила |
|---|---|---|---|
| Скіли записано без втрати змін | manifest, install-вивід | інвентар та хеші після запису; regression конфліктів | механічна, у межах проєкту |
| Runtime відповідає потрібному релізу | manifest, doctor | версія + інвентар/хеші копії проти джерела install | цілісність, не підпис джерела |
| Runtime не звертається до npm | acceptance transcript | запуск без registry/cache та trace subprocess | пряма для сценарію |
| Конфігурацію дозволів записано | локальний setup-звіт | точний diff, згода, повторне читання конфігурації | не доводить застосування хостом |
| Правило завантажене хостом | матриця сумісності | native policy check/діагностика з версією хоста | лише в зафіксованому scope |
| Хост бачить скіли | матриця сумісності | перелік скілів від нової сесії хоста | не випливає з наявності файлів |
| Reviewer executable знайдено | doctor | lookup PATH/PATHEXT чинним resolver | не доводить auth або модель |
| Cross-review дозволено й завершено | acceptance transcript, report | запуск у новій сесії, policy outcome, valid marker/report | спостереження для цього контексту |
| Встановлення потребує дії | exit 6, покомпонентний звіт | конкретний відсутній доказ/обмеження | явний неповний стан |
| Хости обрано користувачем | `selectedHosts`, локальна конфігурація | явний аргумент або збережений вибір setup; вивід називає джерело | декларативний scope, не дозвіл і не повнота release-матриці |
| Активна generation відома | локальний runtime pointer, doctor | шлях під version/digest, інвентар і хеші поточної копії | локальний стан, не межа довіри |
| Claude-шлях не змінився | тест тексту скілів, smoke `--claude` | рядки запуску байт у байт як до зміни; exit-коди й відсутність runtime та записів у налаштування Claude | механічна; pickup Claude — лише в матриці сумісності |
| Дві команди запуску узгоджені | перевірка випуску | однакові підкоманди й прапори в рядках Codex та `npx`; required-version дорівнює package version | механічна, на момент випуску |
| Linked worktree знаходить runtime | acceptance-матриця, doctor | шлях через `git --git-common-dir` під version/digest, інвентар і хеші | локальний стан, не межа довіри |
