# Публікація в npm як `@ysilvestrov/detent` і безпечна команда в правилах

Дата: 2026-11-02
Статус: затверджено 2026-11-02

## Для власника

### Мета

detent знову можна встановити на npm 12, а агент, який виконує правила, запускає тільки пакет
із твого скоупа, а не те, що колись може з'явитися під чужою назвою.

### Що зміниться для тебе

- **Новий обов'язок:** кожен реліз ти публікуєш сам, `npm publish` із 2FA. Агент цього не робить.
- **Без тебе:** проєкти без залежності отримують нову версію одразу після публікації, без PR і
  без оновлення.
- **Незворотно:** опубліковану версію не можна перевикористати, а зняти її npm дозволяє лише
  обмежено. Помилковий реліз виправляється наступною версією.
- **Після мерджа, вручну:** тег `v0.3.0`, публікація, оновлення плагіна detent у Claude, бо
  скіли плагіна до того кажуть `npx detent`.

### На чому стоїть рішення

- Правила мають працювати і в проєкті без залежності. `[вимога власника]`
- Пакет називається `@ysilvestrov/detent`, команда лишається `detent`. `[вимога власника]`
- Випуск вручну з 2FA, без CI. `[вимога власника]`
- npm відмовляє в назві `detent` через схожість із `dedent`, `dotenv`, `redent`. `[проба]` (П-1)
- Сторонньому авторові, ймовірно, npm теж відмовить у назві `detent`. Це припущення: проба
  показала відмову лише тобі, і чи діє перевірка однаково для всіх, невідомо. Рішення на цьому не
  стоїть: нова форма не звертається до цієї назви. Від нього залежить лише захист старих блоків
  до їх оновлення. `[виведення]`
- Форма `npx -y @ysilvestrov/detent` бере локальну залежність, якщо вона є, і завантажує
  найновішу версію, якщо немає, на npm 11 і 12. Перевірено на чужому пакеті такої самої форми і
  на нашому тарболі, бо наш пакет ще не опубліковано. `[проба]` (П-2, П-3)
- `detent install` переписує блок, поставлений старою версією, якщо блок не редагували. `[проба]` (П-4)
- У власному репо detent форма зі скоупом не працює, а `npx detent` працює. `[проба]` (П-5)

### Ключові рішення

1. **Скоуп `@ysilvestrov/detent`.** Відкинуто `detent-cli`: сусідні назви може зайняти хтось
   інший, і перевірка на схожість могла б відхилити її теж.
2. **Одна форма `npx -y @ysilvestrov/detent` у всіх правилах.** Відкинуто `npx --no-install
   detent`: без залежності вона лише падає, а правила мають там працювати.
3. **Без закріпленої версії в правилах.** Відкинуто `@<версія>` у тексті: скіли плагіна статичні
   і не знають версії проєкту, а закріплює версію локальна залежність.
4. **Установку з git прибрано з документації.** Відкинуто збереження як запасного шляху: на
   npm 12 вона вимагає `allow-git=all`, а без нього падає весь `npm ci` проєкту.

Розглянуто стандартне: запит у підтримку npm на назву `detent` — відкинуто, бо це повільно,
результат не гарантований, а другий дефект увесь цей час лишається відкритим.

Розглянуто стандартне: публікація через GitHub Actions із provenance — відкинуто на зараз, бо
випуски рідкі, а CI в репо немає; додати можна окремою зміною.

### Що стане гірше

- Команда в правилах довша.
- Проєкт без залежності завжди на найновішій версії, тож помилковий реліз доходить до нього
  одразу. Захист: локальна залежність.
- Довіра тримається на одному npm-акаунті, а зв'язок пакета з тегом ніде не зафіксований.
- Назва `detent` тобі не належить. Старі блоки зараз отримують 404, але якщо хтось займе назву,
  неоновлений блок запустить чужий код. Цей залишковий ризик зміна не закриває.
- Старі копії не виправляться самі: хтось має запустити `install`. Проєкти з git-залежністю на
  npm 12 мають самі замінити її.
- Між мерджем і публікацією правила в `main` посилаються на пакет, якого ще немає.

### Оцінка

Власник: S. Автор: L. Розбивка: тексти правил і тести близько 40%, README й інструкція випуску
близько 25%, `package.json` і виняток для власного репо близько 15%, перевірка випуску й
публікація близько 20%.

Дешевший варіант: опублікувати пакет, не міняючи правил. Втрачає вимогу власника: у проєкті без
залежності `npx detent` лишається помилкою 404.

Розбіжність на два розміри розібрано з власником: за обсягом коду це S (один PR, до чотирьох
задач), а L дає лише правило шкали про крок людини поза репо, тобто `npm publish`. Прихованої
складності немає. Записуємо L за шкалою, з приміткою, що код розміру S.

## Тіло

### Контекст

Блок конституції, скіли й README кажуть `npx detent`. Без локальної залежності `npx` шукає
пакет `detent` у реєстрі, а він нікому не належить. На npm 12 (`allow-git=none`) обидві форми
установки з README падають з `EALLOWGIT`. Спека релізу 1 відклала npm як окреме питання; ця спека
його закриває.

### Що змінюється

**`package.json`:**
- `name` → `@ysilvestrov/detent`, `version` → `0.3.0` (рішення автора: зміна для користувачів, а
  версія ще 0.x);
- додати `repository` і `publishConfig.access: "public"`, щоб `--access` не треба було пам'ятати;
- `prepare` → `prepack` (рішення автора): `dist/` більше не збирається під час установки, а без
  git-установки `prepare` не потрібен. Він же дає попередження `install-scripts` (П-3). Чи зникне
  попередження, перевіряє план.

**`.claude-plugin/plugin.json`:** `version` → `0.3.0`; `src/plugin.test.ts` вимагає, щоб вона
збігалася з версією пакета.

**`detent.json`:** `"gate": "npm run gate"`. Без `prepare` свіжий checkout не має `dist/`, а типовий
gate (`npm test && npm run typecheck`) його не збирає, тоді як `npm run gate` збирає. Інакше
`npx detent` і `node dist/cli.js` у самому репо не працюватимуть.

**Текст команди** (`npx detent` → `npx -y @ysilvestrov/detent`):
- `constitution/constitution.md`;
- `src/install/blocks.ts`, `BLOCK_BEGIN`; версія маркера лишається `v1`, бо `BEGIN_RE` приймає будь-який
  текст після неї (П-4);
- `skills/cross-review/SKILL.md`, `skills/design-spec/SKILL.md`, `skills/design-spec/spec-format.md`,
  `skills/dev-cycle/SKILL.md`;
- тести, що фіксують ці рядки: `src/content.test.ts`, `src/install/blocks.test.ts`,
  `src/install/plan.test.ts`, `src/commands/install.test.ts`.

Історичні спеки й плани не правимо: це запис того, що було.

**README:**
- розділ установки: `npm i -D @ysilvestrov/detent` і одноразово `npx -y @ysilvestrov/detent install`;
- прибрати рядки про git-установку, `prepare` і попередження `install-scripts` у розділі обмежень;
- перехід зі старої установки: замінити git-залежність (`npm rm detent`, потім
  `npm i -D @ysilvestrov/detent`), запустити `install`; блок, змінений вручну або без запису в
  маніфесті, дає конфлікт і нічого не пише (П-4), його треба полагодити руками;
- обмеження: скіли плагіна Claude оновлюються разом із плагіном, а не через `install`;
- випуск: розділ для власника (тег, чистий checkout, `npm publish`, перевірка shasum).

**`detent.json`, `reviewContext`:** у цьому репо скіли кажуть форму зі скоупом, а запускати треба
`npx detent` або `node dist/cli.js` (П-5). Це такий самий відомий виняток, як інші, що там уже описані.

### Порядок випуску

### Проби

Усі запущено 2026-11-02 на Windows 11, npm 11.20.0 і npm 12.2.1. Проби в чистих теках.

**П-1. Відмова в назві.** Власник запустив `npm publish` для чистого checkout `v0.2.1`:

```
npm error 403 403 Forbidden - PUT https://registry.npmjs.org/detent - Package name too similar to
existing packages dedent,dotenv,redent; try renaming your package to '@ysilvestrov/detent'
```

`npx -y detent --version` у порожній теці після цього: `E404`, код виходу 1.

**П-2. Форма зі скоупом** на `@vercel/ncc` (скоуп, один бінарник, назва бінарника не збігається з
назвою пакета):

```
локальна 0.38.0:              npx -y @vercel/ncc version -> 0.38.0 (і з підтеки)
без залежності:               npx -y @vercel/ncc version -> 0.45.0 (npm view: 0.45.0)
npm 12.2.1, allow-git=none:   npm exec -y -- @vercel/ncc version -> 0.38.0
```

**П-3. Наш тарбол** (`v0.2.1` з іменем `@ysilvestrov/detent`) у чистому проєкті: `npm i -D` на
npm 12.2.1, потім `npx -y @ysilvestrov/detent --version` → `0.2.1`; `npm ci` на npm 12.2.1 →
`added 1 package`. Під час установки було попередження `install-scripts`. Запуску саме з реєстру
ця проба не покриває: його покриває крок 4 випуску.

**П-4. Перепис блоку.** `install --claude` кліном `v0.2.1`, коміт, потім `install --claude`
копією, де `npx detent` замінено на нову форму в конституції та `BLOCK_BEGIN`:

```
update    CLAUDE.md
update    .detent/manifest.json
after: bare=0 scoped=2
```

Блок із чужим текстом і без запису в маніфесті:

```
install: conflict: CLAUDE.md: the constitution block differs from what detent would write and has no manifest record
install: nothing written; ...
```

**П-5. Власний репо.** Копія репо з новим `name`, у її корені:

```
npx detent --version                  -> 0.2.1
npx --no-install detent --version     -> 0.2.1
node dist/cli.js --version            -> 0.2.1
npx -y @ysilvestrov/detent --version  -> 'detent' is not recognized as an internal or external command
```

`npx detent` у нинішньому репо теж друкує `0.2.1`, тож перехресне рев'ю в самому репо працює і далі.
Проба лише на Windows; на іншій ОС текст помилки може бути іншим.

### Що лишається автору плану

- Точні формулювання README.
- Чи прибирає `prepack` попередження `install-scripts` (проба в плані; якщо ні, запис лишається в
  обмеженнях).
