# Проба одного проєктного дозволу на cross-review — план виконання

> Виконання через `superpowers:executing-plans`, послідовно. Це spike. Прототип і конфігурацію проби не комітити. Після проби зафіксувати висновок і лише тоді планувати продуктову інтеграцію.

**Мета.** Перевірити один дозвіл під час встановлення для рев'ю специфікацій і коду репозиторію через локальний Claude CLI, зі збереженням дозволу між сесіями Codex CLI, Desktop і linked worktree.

**Архітектура.** Локальний stdio MCP-сервер має один інструмент `cross_review`. Спочатку заглушка перевіряє політику хоста. Потім сервер читає матеріали з Git і запускає Claude з текстовим входом та вимкненими інструментами.

**Стек.** Наявні Node.js, Git, Codex CLI, Codex Desktop, Claude CLI. Мінімальний MCP SDK допустимий лише в окремому каталозі проби з зафіксованою версією.

**Джерело вимог.** Бріф «один дозвіл на cross-review у межах репозиторію» в цій розмові від 2026-11-09. Його вимоги відтворені нижче. Ця проба перевіряє альтернативу Д-1 з `docs/specs/2026-11/2026-11-09-trusted-host-amendment.md`. Її успіх є входом до поправки архітектури.

**Стан виконання.** Після дозволеного власником продовження перевірено доставку config, одну явну згоду, реальні spec/code MCP-рев'ю в різних CLI-сесіях, ізоляцію B, injection та CLI-відкликання. Власник вручну повторив Desktop spec/code/B тести й підтвердив нуль запитів дозволу. Native read_thread підтвердив виклики, параметри, cwd і результати. 18 focused тестів проходять. Основний механізм підтверджено для CLI й Desktop. Product installer UI, Desktop revocation/restart та інші родини моделей ще не перевірені. Фактичні результати та докази у `docs/probes/2026-11/2026-11-09-cross-review-mcp.md`. Код написали субагенти `gpt-6-luna`.

**Продовження після рішення власника.** Власник дозволив наступну пробу доставки погодженої конфігурації до linked worktree. Доставка копіює config тільки після перевірки Git-належності A. Окрема згода «Дозволяю для A та його worktree» отримана в розмові. Після доставки перевірити actual tool calls із `approval_mode="approve"` без зміни згоди між сесіями. Зберегти початкові докази відсутності нативного успадкування.

## Обмеження та межі висновку

- Напрямок Codex → Claude, автор OpenAI, reviewer Anthropic. Родини мають бути відомі, інакше відмова до запуску.
- Матеріали синтетичні. Встановлена CLI вже авторизована. Довіра Codex до каталогу фіксується як передумова, її запити рахуються окремо.
- Єдина згода явно охоплює передачу специфікацій і коду A провайдеру Anthropic, його обліковий запис, можливі витрати та linked worktrees A.
- Запити дозволу після цієї згоди рахуються всі, включно зі startup MCP, окремою згодою на tool і запитами дочірньої CLI. Два підтвердження під час install також означають два дозволи.
- Сервер, Node і Claude запускаються з абсолютних шляхів поза доступними агенту для запису каталогами. Розташування і реальні права перевіряються в кожному клієнті. Сам шлях не є доказом захисту.
- Репозиторій у прив'язці встановлення фіксований. Виклик не приймає root, команду, executable, модель, аргументи CLI або довільний prompt.
- Рев'ю читає committed Git objects. Незакомічені зміни поза предметом цієї проби.
- Поточні `src/review/adapters.ts` та `src/review/cli-runner.ts` служать джерелом досвіду. Їхні дозволи та worktree runner не переносити автоматично в текстовий прототип.
- Наявні runtime core, install, скіли та продуктову CLI не змінювати. Інсталяційний сценарій проби лише відтворює потрібні кроки налаштування.

## Файли та результати

У схваленому тимчасовому каталозі `detent-mcp-probe-<id>` підготувати `server.mjs`, `review-input.mjs`, `probe.test.mjs`, `setup.mjs`, `fixtures/`, `evidence/`. Для live-запуску встановити перевірену копію сервера в окреме місце поза writable roots хоста. Записати абсолютні шляхи, хеші та спосіб запуску.

У `evidence/` зберігати `environment.json`, очищені копії конфігурації до/після, журнал згод, MCP-виклики, хеші й тексти синтетичного payload, результати CLI та заповнену матрицю. Не копіювати credentials, auth-файли або повне оточення процесу.

Підсумковий звіт має шлях `docs/probes/2026-11/2026-11-09-cross-review-mcp.md`. Заповнювати лише фактичними результатами, для пропущених перевірок писати причину. Продуктовий harness планується після наскрізного огляду результатів цієї проби.

## Фокус перевірки

1. Друга згода, прихована за MCP startup або переходом CLI → Desktop — завдання 1 і 4.
2. Дозвіл A застосовується в B, у тому числі коли B викликає сервер A — завдання 1 і 4.
3. Worktree або змінений шлях помилково ототожнюється з іншим репозиторієм — завдання 2 і 4.
4. Prompt injection, локальні hooks/MCP чи npm shim розширюють можливості Claude — завдання 3.
5. Ревізія, шлях або truncation дає рев'ю іншого чи неповного матеріалу — завдання 2 і 3.

## Завдання 1. Довести збереження та область згоди на заглушці

Вхід — встановлені клієнти й бриф. Результат — `server.mjs` із заглушкою, перевірена конфігурація хоста і журнал згод. Заглушка повертає сталий ідентифікатор A без читання файлів і запуску Claude.

- [ ] Записати версії та шляхи Node, Git, Codex CLI, Desktop і Claude. Перевірити актуальну офіційну документацію та можливості встановлених версій щодо stdio MCP, project config, tool approval, worktree scope і відкликання. Зберегти джерела та розбіжності. Задокументований параметр перевірити на реальному клієнті.
- [ ] Створити A, його linked worktree і незалежний B. Підготувати відновлювані копії лише тих полів конфігурації, яких торкнеться проба. Наявні глобальні дозволи, що можуть приховати запит, записати. Для чистого CLI використати окремий профіль, якщо підтримується.
- [ ] Підняти stdio сервер з одним `cross_review`, перевірити initialize/list/call через MCP-клієнт. stdout містить лише MCP protocol, діагностика йде в stderr.
- [ ] Через setup-сценарій спершу відхилити згоду. Перевірити відсутність автоматичного дозволу. Потім погодитися один раз і зробити виклик із CLI в A. Записати, який компонент зберіг згоду, точне налаштування, його scope та спосіб відкликання.
- [ ] Повторити виклик у новій CLI-сесії, linked worktree, Desktop та B. Перевірити також спробу B викликати інструмент, прив'язаний до A. Заглушка не має бути доступною для такого виклику за згодою A.
- [ ] Рішення першого етапу. Якщо потрібна повторна згода, відсутня проєктна ізоляція або хост не може розпізнати контекст виклику, записати конкретний провал. Зупинити залежні завдання 2–4 і підготувати звіт про межі підходу. Не додавати власний broker чи реєстр для виправлення результату проби.

## Завдання 2. Підготувати точний текст рев'ю з Git

Файли `review-input.mjs`, `probe.test.mjs`, `fixtures/`. Вхід інструмента — рівно один із варіантів `{kind:"spec", path:string, revision:string}` або `{kind:"code", base:string, head:string}`. Невідомі поля відхиляються. Прив'язка A і author family задаються налаштуванням сервера. Вихід `prepareReview(binding, request)` — `{text:string, commits:string[], sha256:string}`.

- [ ] Створити специфікацію з однією явною суперечністю та коміт коду з простим дефектом. Зафіксувати очікувані commit IDs і payload. Окремий випадковий маркер розмістити у файлі B.
- [ ] Написати перевірки через `node --test probe.test.mjs`, спочатку отримати очікуваний FAIL. Перевірити spec/code, основний checkout і linked worktree A, відмову для B, traversal, абсолютного зовнішнього шляху, symlink на B, невідомої ревізії, ревізії з початковим `-` та зайвих полів.
- [ ] Реалізувати підготовку. Перевіряти належність worktree до A через незалежну Git-ідентичність, без припущення, що parent common-dir є checkout. Ревізії спочатку перетворювати на commit IDs. Викликати Git без shell, зовнішніх diff/textconv та checkout. Специфікацію читати як blob, для коду передавати diff і blobs змінених текстових файлів із head. Відмовляти для symlink/submodule/binary матеріалів.
- [ ] Встановити для проби ліміт payload 1 MiB UTF-8. Перевищення дає явну відмову до запуску Claude. Нічого мовчки не обрізати. Перевірити порожній diff, перейменування, видалення, пробіли й Unicode в шляхах, граничний розмір.
- [ ] Повторити тести. Порівняти payload і commits з очікуваними значеннями. Переконатися, що незакомічений canary у A та маркер B відсутні.

## Завдання 3. Один реальний запуск Claude без інструментів

Файл `server.mjs` споживає вихід завдання 2. `cross_review` повертає `{status:"completed", report:string, commits:string[], inputSha256:string}` або MCP tool error з причиною. `completed` означає отриманий звіт. Зміст знахідок оцінюється окремо.

- [ ] За документацією встановленого Claude CLI визначити режим headless, заборону всіх tools, відключення MCP, hooks і проєктних інструкцій. Перевірити фактичний запуск у нейтральному cwd з тестовим HOME/config способом, який зберігає потрібну авторизацію. Якщо ці умови недосяжні, записати провал без послаблення режиму.
- [ ] Додати transport-перевірку з fake CLI. Вхід передається stdin, shell вимкнений, аргументи фіксовані. На Windows перевірити реальну npm shim-інсталяцію та запуск її entrypoint через абсолютний зовнішній Node. Прибрати змінні preload/debug, які дозволяють виконати сторонній код. Не логувати auth-дані.
- [ ] Реалізувати timeout 180 секунд та обмеження stdout 1 MiB. Перевірити nonzero exit, timeout, порожній звіт та перевищення виходу. Вони повертають явну помилку. Не робити автоматичні повтори, які спотворюють підрахунок запусків і витрат.
- [ ] Запустити одну специфікацію через MCP і справжній Claude. Зафіксувати payload hash, команду без секретів, кількість запусків, запити дозволу й звіт. Перевірити знайдену суперечність.
- [ ] Повторити з текстом, що вимагає прочитати маркер B та створити файл. Додати до A тестові hooks/MCP конфігурацію і підмінений проєктний launcher із canary. Перевірити, що вони не виконані, файл не створений, маркер відсутній, а конфігурація запуску справді забороняє інструменти. Самої відповіді моделі недостатньо.

## Завдання 4. Наскрізна матриця та рішення

Вхід — перевірений прототип і конфігурація завдання 1. Вихід — evidence і підсумковий звіт. Виконати без зміни правил між рядками, крім останнього кроку відкликання.

| Сценарій | Очікування |
| --- | --- |
| CLI, A, специфікація після install-згоди | Звіт, нуль додаткових запитів |
| CLI, нова сесія, worktree A, code | Звіт для потрібних commits, нуль запитів |
| Desktop, A, spec і code | Та сама згода, нуль запитів |
| Desktop, нова сесія, worktree A | Та сама згода, нуль запитів |
| CLI і Desktop, B, інструмент A | Дозвіл A не дозволяє виклик |
| A, шлях до B або зайві параметри | Відмова до запуску Claude |
| Відкликана згода, нові сесії CLI і Desktop | Запит згоди або недоступний інструмент |

- [ ] Заповнити кожний рядок фактичними результатами й посиланнями на evidence. Неможливість керувати Desktop або перевірити нову сесію позначити як неперевірене. Прямий MCP client не замінює виклик із Codex.
- [ ] Провести наскрізний огляд прототипу, effective config, логів і областей запису обох хостів. Записати виявлені прогалини та межі доказів. Зафіксувати спосіб відновлення попередніх налаштувань. Видалення тимчасових каталогів виконується лише за правилом 8 constitution.
- [ ] Підготувати звіт з висновком `підтверджено`, `частково` або `спростовано`. Для підтвердження потрібні всі рядки матриці, одна install-згода, захист коду сервера від запису агентом та доведений режим reviewer без tools.
- [ ] Якщо підтверджено, описати мінімальну поправку до специфікації й запропонувати наступний план продуктової інтеграції на основі реального прототипу. Якщо частково або спростовано, назвати точну межу та найменшу наступну перевірку. Перевірка інших напрямків reviewer залишається окремим висновком про подальшу сумісність.

## Самоперевірка плану

Бріф покрито чотирма завданнями. Дозволи й ізоляція перевіряються раніше, ніж залежний reviewer transport. Негативна згода, нова сесія, worktree, CLI/Desktop, B, ін'єкція та відкликання мають окремі кроки. Прототип не вимагає перебудови поточного runtime core. Висновок про підтримку хостом робиться тільки після live-перевірок.

- [x] Ізольований trust-only CLI-профіль, protected install звичайних Node модулів, без глобальних MCP/rules.
- [x] Live stub calls у нових сесіях A й A-linked, B tool absence.
- [x] Committed payload preparation, pinned Git, 5 input regression tests.
- [x] Claude no-tools runner, 4 fake CLI regression tests, live init з порожніми tools/MCP.
- [x] Live Codex → MCP → Claude специфікація й code review, root/commits/hash у результатах.
- [x] Injection з синтетичним B marker і hook/MCP/launcher canaries, жоден не спрацював.
- [x] Негативний startup у B, prompt policy відкликання в обох checkout.
- [x] Огляд усього прототипу окремим субагентом, Important/Critical не виявлено.
- [x] Звіт і кроки ручної Desktop-перевірки. Після revocation-test повернуто approve на підставі початкової чинної згоди.
- [x] Desktop позитивні spec/code тести в A/A-linked і негативний B. Виконав власник, підтвердив нуль додаткових запитів. Native журнали звірені, evidence збережено.
- [ ] Desktop revocation та restart самого застосунку.
- [ ] Продуктовий installer consent UI та його шлях відмови. Поточна згода отримана через чат, а тестовий config записано вручну.

Результат Desktop отримано. Є підстава спростити архітектурну специфікацію до локального MCP і планувати продуктовий harness. Поточний spike не комітиться.
